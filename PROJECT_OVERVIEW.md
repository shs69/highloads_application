# Как устроен проект

Это учебный стенд HTTP-балансировки: он показывает, как направлять запросы на более быстрый сервер, замечать изменение его скорости и переживать отказ. Основной алгоритм — **Least Time с оценкой времени ответа через EWMA**.

Здесь — поведение системы и смысл экспериментов. Конкретные методы и механика библиотек разобраны в [CODE_WALKTHROUGH.md](CODE_WALKTHROUGH.md).

## 1. Из чего состоит система

```text
Генератор нагрузки → балансировщик :8080 → A :9001 — задержка  50 мс
                                       → B :9002 — задержка 100 мс
                                       → C :9003 — задержка 150 мс
```

| Компонент | Ответственность |
| --- | --- |
| Три бэкенда | Имитируют работу заданной задержкой, отвечают на проверку доступности, позволяют менять своё поведение. |
| Балансировщик | Выбирает бэкенд, пересылает запрос, измеряет ответ, ведёт оценки и проверяет доступность. |
| Генератор | Отправляет заданное число запросов и сохраняет результаты в JSON. |
| `compare_ewma` | Отдельно сравнивает коэффициенты сглаживания на фиксированной последовательности измерений, без HTTP. |

Компоненты запускаются отдельными процессами. Внутри серверов конкурентную работу обеспечивает `asyncio`; HTTP-сервер и HTTP-клиент реализованы через `aiohttp`. Состояние балансировщика хранится в памяти и сбрасывается при перезапуске.

## 2. Путь одного запроса

Перед началом приёма клиентов балансировщик **последовательно** отправляет каждому бэкенду `GET /work?request_id=0`. Успешная проба разрешает назначения на сервер и задаёт начальную оценку его скорости. Неуспешная оставляет сервер недоступным. Эти пробы не входят в счётчик клиентских назначений.

Дальше для каждого `GET /work?request_id=42` происходит следующее:

1. Проверяется ID: одно целое положительное число. Ноль зарезервирован для внутренних проб.
2. Выбирается доступный бэкенд и фиксируется номер назначения.
3. Запрос пересылается на его `/work`; балансировщик ждёт **всё тело ответа**.
4. Полный HTTP 200 обновляет оценку, если сервер всё ещё считается доступным. Ошибки и отмены оценку не меняют.
5. Клиент получает статус и тело ответа, например `{"request_id":42,"backend_id":"A"}`, плюс диагностические заголовки `X-Backend-ID`, `X-Assignment-Number`, `X-Selection-Mode`, `X-EWMA-Before` и `X-EWMA-After`.

Назначение не означает успех: запрос мог уйти на A и завершиться HTTP 500 или тайм-аутом. Повторной отправки на другой сервер нет.

## 3. Как выбирается сервер

Обычно побеждает доступный сервер с минимальным `estimate`. При одинаковых оценках — первый по лексикографическому порядку ID; для штатного конфига это A, B, C.

`estimate` — экспоненциально взвешенное среднее, **EWMA**:

```text
новая оценка = alpha × измеренное время + (1 − alpha) × старая оценка
```

При `alpha=0.2`, старой оценке A в 50 мс и новом ответе за 500 мс получается `0.2×500 + 0.8×50 = 140 мс`. Если оценка B осталась 100 мс, следующий обычный запрос уйдёт на B. При `alpha=0.8` A получил бы оценку 410 мс: большой коэффициент быстрее реагирует на изменения, но сильнее зависит от отдельных измерений.

**Зачем нужен исследующий обход.** Если всегда выбирать минимум, ранее медленный сервер перестанет получать запросы. Его оценка не улучшится даже после ускорения. Поэтому каждое `exploration_interval`-е назначение идёт по отдельному циклу доступных серверов. При значении 10 и доступных A/B/C: назначение №10 → A, №20 → B, №30 → C, №40 → A. Обычные назначения этот цикл не двигают.

Здесь скорость оценивается по завершённым ответам. Число активных запросов и `weight` **не участвуют в выборе**. Поэтому при одновременном приходе множества запросов большая их часть может попасть на один быстрый бэкенд ещё до появления новых измерений.

## 4. Отказ, восстановление и HTTP-ошибки

`/health` отвечает, доступен ли бэкенд. `/work` выполняет имитируемую работу. Это разные сигналы: `/health` может возвращать 200, пока `/work` медленный или отвечает 500.

С параметрами по умолчанию переходы выглядят так:

```text
Доступен
  → две неудачные проверки /health подряд
  → исключён из новых назначений
  → завершились все ранее назначенные запросы
  → две успешные проверки /health подряд
  → успешная проба /work?request_id=0
  → снова доступен, оценка заменена временем новой пробы
```

Промежуточный успех сбрасывает серию неудач, промежуточная неудача — серию успехов. Пока у исключённого сервера есть старые запросы, проверки для его восстановления не запускаются. Неуспешная рабочая проба оставляет сервер исключённым и требует новой серии успешных проверок.

| Что произошло | Что увидит клиент |
| --- | --- |
| Неверный `request_id` | 400, без назначения бэкенда. |
| Нет доступных бэкендов или балансировщик прекращает работу | 503, без назначения. |
| Ошибка соединения с выбранным бэкендом | 502, с метаданными назначения. |
| Истёк тайм-аут обращения к бэкенду | 504, с метаданными назначения. |
| Бэкенд вернул ошибочный HTTP-статус | Этот статус передаётся клиенту; в том числе 500 или 503. |

Следствие выбранной политики: серия HTTP 500 или тайм-аутов `/work` сама по себе не исключает сервер и не повышает его EWMA. Если `/health` продолжает отвечать 200, сервер остаётся кандидатом. Эксперимент с отказом и эксперимент с замедлением проверяют разные механизмы.

## 5. Как запустить и провести эксперимент

Из корня проекта установите зависимости: `uv sync --locked`. Нужен Python 3.13+. Затем выполните **каждую строку в отдельном терминале**, сначала запустив бэкенды:

```bash
uv run python -m highloads_applications.backend --id A
uv run python -m highloads_applications.backend --id B
uv run python -m highloads_applications.backend --id C
uv run python -m highloads_applications.balancer
```

В ещё одном терминале:

```bash
curl -i 'http://127.0.0.1:8080/work?request_id=1'
uv run python -m highloads_applications.loadgen \
  --mode sequential --requests 600 --output results/sequential.json
uv run python -m highloads_applications.loadgen \
  --mode concurrent --requests 600 --concurrency 20 --output results/concurrent.json
```

В `sequential` следующий запрос начинается после завершения предыдущего. В `concurrent` одновременно выполняется до `concurrency` запросов; освободившееся место занимает следующий. Это ограничение одновременности, **не заданная частота запросов в секунду**.

Настройки лежат в [configs/system.toml](configs/system.toml). Все компоненты принимают `--config`; генератор также позволяет переопределить URL, режим, число запросов, конкурентность, тайм-аут и путь отчёта.

| Настройка по умолчанию | Значение и смысл |
| --- | --- |
| `alpha`, `exploration_interval` | 0.2 и 10: сглаживание и частота исследующих назначений. |
| `request_timeout` | 2 с на обращение балансировщика к бэкенду, включая чтение тела. |
| `health_interval`, `health_timeout` | Пауза 1 с между проверками одного бэкенда; до 0.3 с на проверку. |
| `failure_threshold`, `recovery_threshold` | По две последовательные проверки для исключения и начала рабочей пробы. |
| `loadgen.timeout` | 3 с на запрос генератора к балансировщику. |
| `shutdown_timeout` | До 5 с ожидания текущих рабочих задач при остановке балансировщика, затем их отмена. |

TOML перечитывается при запуске процесса. Путь отчёта из TOML отсчитывается от каталога конфига; путь `--output` — от текущего рабочего каталога.

Для изменения поведения работающего бэкенда есть локальный административный маршрут:

```bash
# Замедлить A с 50 до 500 мс.
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' -d '{"delay_ms":500}'

# Вернуть исходное состояние.
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' \
  -d '{"delay_ms":50,"available":true,"work_status":200}'
```

Другие полезные тела запроса: `{"available":false}` для отказа, `{"work_status":500}` для ошибки работы, `{"delay_ms":2500}` для превышения штатного тайм-аута балансировщика. Изменения влияют на новые запросы. Маршрут существует только при привязке сервера к loopback и принимает только локальных клиентов.

Для сравнения `alpha` сначала используйте `uv run python -m highloads_applications.loadgen.compare_ewma`: CSV содержит одну трассу 50 → 500 → 50 мс для коэффициентов 0.2 и 0.8. Для сетевого сравнения проведите серии «исходная скорость → замедление → восстановление», затем поменяйте `alpha`, перезапустите балансировщик и повторите те же серии. Фиксированная трасса сравнивает формулу; сетевой опыт — весь контур, где выбор сервера влияет на поступление новых измерений.

## 6. Как понимать результат

JSON содержит `parameters`, `summary` и записи отдельных запросов в `requests`.

| Поле | Как читать |
| --- | --- |
| `assignments_by_backend` / `successful_by_backend` | Сколько назначений удалось наблюдать / сколько запросов завершилось HTTP 200 без клиентской ошибки. |
| `http_errors` / `client_errors` | Полученные ошибочные статусы / ошибки на стороне генератора. Один запрос может попасть в обе категории, например при обрыве чтения тела ответа с HTTP 500. |
| `without_assignment_metadata` | Нет заголовка с бэкендом. Это бывает как при 503 без назначения, так и при потере ответа после назначения. |
| `latency_seconds` | Задержки всех результатов, включая ошибки. Ожидание разрешения семафора перед отправкой сюда не входит. |
| `requests_per_second` | Число результатов, включая неуспешные, делённое на длительность всей серии. |

`request_id` начинается с 1 в каждом запуске генератора. `assignment_number` общий для балансировщика до его перезапуска; даже предварительный `curl` сдвигает эту нумерацию. Заголовки и JSON содержат времена в **секундах**, тогда как `delay_ms` задаётся в миллисекундах.

Не путайте два измерения: EWMA использует участок «балансировщик → бэкенд → балансировщик», а генератор измеряет весь свой HTTP-запрос к балансировщику. Подробную историю назначений можно сохранить, перенаправив stderr балансировщика в файл: `2> results/balancer.log` после создания каталога `results`.

## 7. Что этот стенд позволяет заключить

Он позволяет проверить распределение запросов, реакцию на изменение задержек, исключение и возврат серверов. Но бэкенд имитирует задержку неблокирующим ожиданием и не моделирует очередь ограниченного числа рабочих процессов или насыщение CPU. Полученный RPS поэтому не является оценкой мощности реального сервиса.

Балансировщик обслуживает конкретный `/work` API: буферизует ответ целиком, не проксирует произвольные методы и заголовки, не настраивает TLS и не разделяет состояние между несколькими экземплярами. На участке к бэкендам каждое обращение создаёт новое TCP-соединение, что тоже влияет на измерения.
