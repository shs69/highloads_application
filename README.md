# HTTP-балансер Least Time

Установка зависимостей (Python 3.13+):

```bash
uv sync --locked
```

Запустите бекенды и балансер, каждую команду в отдельном терминале:

```bash
uv run backend --id A
uv run backend --id B
uv run backend --id C
uv run balancer
```

По умолчанию настройки читаются из `configs/config.toml`. Для другого файла
передайте `--config путь/к/config.toml` и бекендам, и балансеру.

```bash
curl -i 'http://127.0.0.1:8080/work?request_id=1'
```

Балансер выбирает доступный бекенд с минимальной оценкой времени ответа.
После успешного ответа оценка обновляется по формуле
`EWMA = alpha * время_ответа + (1 - alpha) * предыдущая_оценка`.
Измерение включает чтение всего тела ответа. Каждое `exploration_interval`-е
назначение идёт на следующий доступный бекенд по кругу: это позволяет заметить
ускорение сервера, который прежде был медленным. При равных оценках выбирается
первый бекенд по ID. Вес и число активных запросов в выборе не участвуют.

При запуске балансер измеряет каждый бекенд запросом `/work?request_id=0`.
Клиент передаёт свой целочисленный `request_id > 0`. Балансер присваивает запросу
собственный последовательный номер начиная с 1, передаёт его бекенду и возвращает
в заголовке `X-Request-ID`. Бекенд возвращает этот же номер в JSON. Исходный номер
клиента сохраняется в `X-Client-Request-ID` и журнале назначения.
Например, два обращения с `request_id=715` получат номера балансера 1 и 2.
Ответы 503 тоже получают номера запросов, но не увеличивают счётчик назначений.
После перезапуска нумерация начинается заново. Номер 0 используется только для проб.
Проверки `/health` выполняются независимо для каждого бекенда. После
`failure_threshold` неудач подряд сервер исключается из выбора. Для возвращения
нужны завершение старых запросов, `recovery_threshold` успешных проверок подряд
и новая успешная проба `/work`. Ошибки `/work` сами по себе не исключают бекенд
и не меняют EWMA.

Балансер передаёт статус и тело ответа бекенда, добавляя заголовки
`X-Backend-ID`, `X-Assignment-Number`, `X-Selection-Mode`, `X-EWMA-Before`
и `X-EWMA-After`. Ошибка соединения возвращает 502, тайм-аут — 504,
отсутствие доступных бекендов — 503. Повторов запросов нет.
При остановке балансер ждёт активные запросы до `shutdown_timeout`, затем
отменяет оставшиеся и закрывает соединения. Все интервалы и тайм-ауты — в секундах.

## Генератор запросов

Генератор обращается к балансеру на порту 8080 и нумерует свои запросы с 1.
Два режима запуска:

```bash
uv run generator --mode sequential --requests 60 --output results/sequential.json
uv run generator --mode parallel --requests 60 --concurrency 20 --output results/parallel.json
```

`--requests` задаёт количество запросов, `--concurrency` ограничивает одновременную
отправку в параллельном режиме. По умолчанию это 1000 запросов и 100 одновременных
обращений. Адрес можно изменить через `--url http://127.0.0.1:8080/work`.
`--timeout` задаёт время ожидания генератора; по умолчанию 3 секунды, чтобы успеть
получить ответ 504 от балансера с его ограничением в 2 секунды.

Без `--output` результаты выводятся в терминал. В JSON сохраняются статус,
длительность, номер клиента, номер балансера и выбранный сервер из `X-Backend-ID`.
Назначения и успешные ответы по серверам считаются отдельно. Ошибка чтения тела
не считается успехом, даже если сервер успел прислать заголовок со статусом 200.
Генератор не повторяет запрос при обрыве соединения.

## Изменение задержки и доступности

У каждого бекенда есть `GET /admin` для просмотра состояния и `POST /admin`
для его изменения. Разрешены поля `delay_ms` (неотрицательное число)
и `available` (`true` или `false`). Настройки действуют до перезапуска процесса.
Некорректный запрос возвращает 400 и не меняет состояние.

Замедление A и возврат к исходной задержке:

```bash
curl -X POST http://127.0.0.1:9001/admin -H 'Content-Type: application/json' -d '{"delay_ms":500}'
curl -X POST http://127.0.0.1:9001/admin -H 'Content-Type: application/json' -d '{"delay_ms":50}'
```

Изменение применяется к новым запросам. Уже принятые запросы завершаются со своей
задержкой. Для наблюдения за переключением выбора запустите последовательную серию
и меняйте задержку во время её выполнения.

Исключение A и восстановление:

```bash
curl -X POST http://127.0.0.1:9001/admin -H 'Content-Type: application/json' -d '{"available":false}'
curl -X POST http://127.0.0.1:9001/admin -H 'Content-Type: application/json' -d '{"available":true}'
```

При `available=false` новые `/work` и `/health` получают 503. Балансер исключит
сервер после двух неудачных проверок. После возврата он дождётся завершения старых
запросов, двух успешных проверок и новой рабочей пробы. Если отключить все три
бекенда и дождаться проверок, балансер вернёт 503 с записью `backend=-` в журнале.

Чтобы сохранить журнал балансера:

```bash
mkdir -p results
uv run balancer 2> results/balancer.log
```

## Сравнение коэффициентов

```bash
uv run --extra plots compare-ewma --output results/ewma
```

Команда сохраняет журнал `measurements.csv` и график `comparison.png`.
Оба коэффициента получают одну последовательность: 10 ответов по 50 мс,
20 по 500 мс и 30 по 50 мс. Это расчёт реакции алгоритма на заданные измерения,
без HTTP-серверов и случайных сетевых задержек. На двух графиках одинаковые шкалы,
пунктир показывает заданное время ответа, цветная линия показывает оценку.
Период замедления выделен фоном.

Для проверки через настоящие HTTP-запросы используйте генератор и `/admin`.
Коэффициент для работающего балансера задаётся в конфигурации полем `alpha`;
после его изменения балансер нужно перезапустить.
