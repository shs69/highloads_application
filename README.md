# HTTP-балансировщик Least Time

Лабораторная по разделу **3. Least Time** задания «Разработка балансировщиков нагрузки».
Python 3.13+, asyncio и aiohttp. Три бэкенда, балансировщик и генератор запросов
запускаются независимо. Зависимости и запуск — через uv.

## Запуск

```bash
uv sync --locked
```

В четырёх терминалах из корня проекта:

```bash
uv run python -m highloads_applications.backend --id A
uv run python -m highloads_applications.backend --id B
uv run python -m highloads_applications.backend --id C
uv run python -m highloads_applications.balancer
```

Проверка и нагрузка:

```bash
curl 'http://127.0.0.1:8080/work?request_id=1'
uv run python -m highloads_applications.loadgen \
  --mode sequential --requests 600 --output results/sequential.json
uv run python -m highloads_applications.loadgen \
  --mode concurrent --requests 600 --concurrency 20 --output results/concurrent.json
```

Все настройки находятся в `configs/system.toml`. Каждый компонент принимает
`--config /path/system.toml`; генератор также принимает `--url` и `--timeout`.
Конфигурация по умолчанию ищется относительно исходников. Из другой директории
можно запускать через `uv run --project /path/to/project python -m ...`.
Изменения TOML применяются при следующем запуске. Неверные поля, типы, диапазоны
и повторяющиеся ID/адреса останавливают запуск с сообщением об ошибке.

## Как работает балансировка

```text
Клиент → 127.0.0.1:8080 → A, 127.0.0.1:9001, задержка  50 ms
                      → B, 127.0.0.1:9002, задержка 100 ms
                      → C, 127.0.0.1:9003, задержка 150 ms
```

Клиент отправляет `GET /work?request_id=1`, бэкенд возвращает
`{"request_id": 1, "backend_id": "A"}`. Задержка реализована через `asyncio.sleep`:
другие запросы и `/health` в это время продолжают обрабатываться.

При запуске серверы по очереди проходят пробу `/work?request_id=0`.
Приём клиентских запросов начинается после завершения этих проб.
Успешная проба задаёт начальную оценку. Для обычных запросов ID должен быть
положительным; внутренние пробы не входят в рабочие счётчики.

Обычно выбирается доступный сервер с минимальной оценкой. При равенстве —
первый по ID, A → B → C. Каждое десятое назначение идёт по независимому циклу:
10-е → A, 20-е → B, 30-е → C, с пропуском недоступных серверов.
После полного HTTP 200 оценка обновляется:

```text
EWMA = alpha × время_ответа + (1 − alpha) × прежняя_оценка
alpha = 0.2: 100 ms → измерение 300 ms → новая оценка 140 ms
```

Ошибки, тайм-ауты и отмены оценку не меняют. Веса сохранены в конфигурации,
но в Least Time не используются. Все изменения состояния выполняются без
`await` в одном event loop; сетевой запрос происходит между выбором и завершением.

## Отказ и восстановление

Проверки `/health` выполняются с интервалом 1 секунда и тайм-аутом 300 ms.
Две неудачи подряд запрещают новые назначения. Старые запросы завершаются
самостоятельно, но их ответы уже не меняют оценку недоступного сервера.

По специальному требованию Least Time восстановление начинается **после
завершения старых запросов**: две новые успешные проверки, затем успешная
проба `/work`. Измерение пробы заменяет старую оценку. Неудачная проба оставляет
сервер недоступным и сбрасывает счётчик восстановления. Пока старые запросы
не завершились, новые проверки этого сервера не запускаются.

Медленный `/work` или его HTTP 500 сами по себе не исключают сервер: доступность
определяется `/health`. Между проверками одного сервера выдерживается заданный
интервал; его восстановительная проба выполняется в той же фоновой задаче.

Для экспериментов есть локальный `POST /admin/state`:

```bash
# Замедление A; для восстановления отправьте delay_ms=50.
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' -d '{"delay_ms":500}'
# Имитация отказа; для восстановления отправьте available=true.
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' -d '{"available":false}'
# Ошибка рабочего запроса; для восстановления отправьте work_status=200.
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' -d '{"work_status":500}'
# Тайм-аут, затем возврат исходных настроек.
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' -d '{"work_status":200,"delay_ms":2500}'
curl -X POST http://127.0.0.1:9001/admin/state \
  -H 'Content-Type: application/json' -d '{"delay_ms":50,"available":true,"work_status":200}'
```

Админский маршрут доступен только при bind на loopback и только локальным
клиентам. Он меняет настройки будущих запросов. Для реального сетевого отказа
остановите процесс бэкенда и запустите его снова той же командой.

## Соединения и завершение

Балансировщик открывает отдельное HTTP/1.1-соединение для каждого исходящего
запроса: `TCPConnector(force_close=True)`. Тайм-аут 2 секунды охватывает подключение
и чтение всего тела. Неудачные запросы не повторяются. Ответы: 503 при отсутствии
серверов, 502 при сетевой ошибке, 504 при тайм-ауте; HTTP 500 передаётся клиенту.

При отключении клиента обработчик отменяется и закрывает исходящее соединение.
SIGINT/Ctrl+C и SIGTERM прекращают приём работы. Балансировщик ждёт текущие
запросы до 5 секунд, отменяет остаток, останавливает проверки и закрывает сессию.
Перезапуск создаёт новые оценки и счётчики. Генератор при отмене закрывает свою
сессию; частичный отчёт не сохраняется.

## Статистика и сравнение alpha

Генератор выводит сводку и сохраняет JSON с результатом каждого запроса:
статус, длительность, бэкенд, номер и режим назначения, EWMA до/после.
Сводка содержит назначения и успешные ответы **раздельно**, ошибки по статусам,
среднее/min/max/p50/p95/p99, длительность опыта и requests/sec.
Время считается для всех завершённых запросов. p50 выводится от 2 измерений,
p95 — от 20, p99 — от 100; используется линейная интерполяция.

Назначения берутся из заголовков балансировщика, включая ответы 500/502/504.
При потерянном ответе сведения могут не дойти — такие случаи отмечены в
`without_assignment_metadata`. Полная история остаётся в логе балансировщика.
ID уникальны внутри запуска генератора; номер назначения растёт до перезапуска
балансировщика. Путь отчёта в TOML считается от конфигурации, `--output` — от CWD.

Сравнение на одной заданной трассе 50 → 500 → 50 ms:

```bash
uv run python -m highloads_applications.loadgen.compare_ewma
# Необязательная зависимость matplotlib нужна только для построения графика.
uv run --group plots python -m highloads_applications.loadgen.compare_ewma \
  --output results/ewma.csv --plot results/ewma.png
```

Это математический эксперимент: 10 быстрых, 20 медленных и 30 быстрых измерений.
После первого замедления оценка равна 140 ms для alpha=0.2 и 410 ms для alpha=0.8.
Большой alpha быстрее реагирует и на замедление, и на восстановление.

Для сетевого опыта установите `alpha` в TOML, перезапустите балансировщик и
выполните три последовательные серии по 200 запросов: A с задержками 50, 500
и снова 50 ms. Сохраните серии через разные `--output`. Повторите с другим alpha.
Сетевые измерения зависят от машины; фиксированная трасса даёт воспроизводимое
сравнение самой формулы.

Лог содержит время, номер назначения, request ID, бэкенд, режим, результат,
длительность и оценки. При конкурентной работе оценка перед завершением может
отличаться от оценки в момент назначения. Пробы и смена доступности записываются
отдельно. Сохранить журнал:

```bash
mkdir -p results
uv run python -m highloads_applications.balancer 2> results/balancer.log
```

## Где читать код и как проверить

- `configuration.py` — параметры и их проверка при создании dataclass.
- `balancer/algorithms.py` — состояние серверов, выбор Least Time, циклический обход и обновление EWMA.
- `balancer/app.py` — передача запросов, измерение времени, восстановление и остановка.
- `backend/app.py` — тестовый сервер и управление задержкой/отказом.
- `loadgen/generator.py` — отправка запросов и статистика.
- `__main__.py` в каждом компоненте — аргументы CLI и запуск.

Начать удобно с `backend/app.py`: внутри `create_app` находятся настройки,
словарь текущего состояния и обработчики трёх маршрутов. Запуск и остановка
записываются в журнал отдельными обработчиками событий.

Затем в `balancer/algorithms.py` читать `LeastTime.select_backend`: здесь выбирается
сервер с минимальной оценкой или следующий сервер циклического обхода. Этот код
не выполняет HTTP-запросы и работает без `async`. Метод `record_response`
обновляет оценку после успешного ответа доступного сервера, используя заданный `alpha`.

В `balancer/app.py` читать `handle_work` → `forward`. Обработчик обращается к
алгоритму за сервером, сохраняет номер назначения и исходную оценку, отправляет
запрос, измеряет длительность и передаёт результат в `record_response`, затем пишет лог.
Блок `finally` освобождает счётчики даже при отмене запроса. В `check_health`
весь порядок восстановления находится в одном месте: дождаться старых запросов,
получить два успешных health check, выполнить рабочую пробу.

В генераторе последовательный режим — цикл с `await`. В параллельном режиме
каждому запросу соответствует одна задача. `Semaphore` допускает к отправке
не более `concurrency` запросов, а `TaskGroup` ждёт их завершения и отменяет
оставшиеся при сбое. Результаты сохраняются в порядке ID без дополнительной
сортировки. Такой вариант рассчитан на учебные серии: число созданных задач
равно числу запросов.

```bash
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

Форматтер проекта — Ruff из dev-зависимостей. Правила заданы в `pyproject.toml`,
длина строки — 100 символов. Применить форматирование ко всему проекту:

```bash
uv run ruff format .
```

В VS Code установите рекомендуемое расширение Ruff (`charliermarsh.ruff`).
Настройки `.vscode/settings.json` включают форматирование Python при сохранении
и выбирают Ruff из `.venv`. Откройте корень проекта как папку и выполните
`uv sync --locked`, чтобы создать окружение с нужной версией форматтера.

Тесты проверяют алгоритм на заданных числах и HTTP на временных локальных портах:
ошибки, восстановление, отмену, закрытие соединений, остановку и по 600 запросов
в обоих режимах. Проект реализует предусмотренный JSON API; произвольные методы,
потоковые тела, TLS и несколько процессов одного балансировщика не поддерживаются.
